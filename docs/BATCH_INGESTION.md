# 成交批次为什么需要原子导入和可重试身份

LedgerX 记录研究成交事实及现金变动。下面使用合成事实验证接入行为，没有真实券商客户或生产交易服务。

## 业务缺口

原有单事件 `append` 能保证这一笔失败不改账，但外部调用者循环追加十笔时，第十笔余额不足，前九笔可能已经留在内存里。另一个问题是上游没有收到成功响应，重新投递同一批；简单拒绝所有重复 ID，无法区分安全重试与同 ID 被换了价格。

新增 `append_batch` 在私有候选账本上验证全批，完整成功后才替换当前账本的余额、持仓、历史及已使用 ID。`ingest` 则完整解析输入、重放已有日志、接受整批，再原子替换日志文件。任何输入或记账错误都不发布前半批；文件替换失败则保留原日志并清理临时文件。命令行失败返回 2，错误写到 stderr，不输出成功结果。

这把业务接入闭合成：**稳定事实 ID → 内容核对 → 全批账务校验 → 原子发布 → 重试复用原记录**。

## 同一个 ID，究竟比较什么

| 情形 | 行为 |
| --- | --- |
| 同 ID、同事件类型、同 UTC 时间、全部经济字段相同 | 返回原日志记录，现金、持仓、序号和头哈希均不重复变化。 |
| `100` 与 `100.00`；相同瞬间的 `Z` 与 `+08:00` | 在 Decimal 数值和已标准化 UTC 时间上比较，属于相同事实；保留第一次保存的表示和哈希。 |
| 同 ID 但金额、价格、数量、费用、方向、标的、时间或类型不同 | 拒绝全批，不偷偷覆盖旧事实，也不当作新成交入账。 |
| 同一批中重复相同事实 | 第一次新事实入账，后面复用这一条；重复行计入 `reused_events`。 |
| 同一批中同 ID 内容矛盾 | 拒绝全批，即使前几行已经在候选账本里验证成功。 |

ID 由上游分配，在整个日志内代表同一个事实。若上游重试时换了 ID，LedgerX 无法知道它其实是同一笔成交。此次没有实现冲正、成交取消或凭证更正工作流；同 ID 经济内容修改会报冲突。

原 `append` 继续严格拒绝重复 ID；日志重放仍逐条调用这个严格入口，不能把重复日志行当作合法重试吞掉。

## 记录顺序和事件时间

输入按给出的行顺序处理，不自动排序。**新事实**必须沿用账本非递减 UTC 时间要求，也不能插入已有历史之前。时间相同可以按输入顺序追加。旧事实重试可以晚到，且无需按旧事实时间重新排列，因为它只是复用原记录，不新记账。

例如新买入在出售之后才被提交，即使排序能让它通过，系统也不会擅自改写上游提供的成交顺序；需要上游先核实完整事实和正确顺序。

## 可直接运行的合成案例

仓库的 [输入文件](../examples/ingestion_events.jsonl) 有四行：10,000 美元入金、买入 10 股 ACME、卖出 4 股，再投递一次相同买入（金额表示带额外零）。

```bash
ledgerx ingest imported.jsonl --events examples/ingestion_events.jsonl
ledgerx ingest imported.jsonl --events examples/ingestion_events.jsonl
ledgerx verify imported.jsonl
```

第一次为 `input_rows=4, appended_events=3, reused_events=1`，第二次为 `appended_events=0, reused_events=4`，完整重试不会重写文件。最终仍是三条日志：现金 **9,438**、历史持仓成本 **600.6**、已实现损益 **38.6**，与原 `demo` 完全一致。

[实际运行输出](../examples/ingestion_result.json)保存了首次导入与完整重试的计数、输入摘要及同一日志头；回归测试从公开输入重新生成这两次输出并比较全部字段。这里的金额及结果均为合成案例。

Windows 可使用 `.\.venv\Scripts\ledgerx.exe` 替换上述命令名。

输入是 UTF-8 JSONL，每行一个原始事件，所有字段均为字符串：

```json
{"kind":"cash","event_id":"fund-001","occurred_at":"2024-01-02T00:00:00Z","direction":"deposit","amount":"10000"}
{"kind":"fill","event_id":"fill-001","occurred_at":"2024-01-03T00:00:00Z","symbol":"ACME","side":"buy","quantity":"10","price":"100","fee":"1"}
```

`cash` 精确包含上例五个字段；`fill` 精确包含上例八个字段。未知字段、重复 JSON 键、数字而非金额字符串、空行、非有限金额、非法事件或无 UTC 偏移时间都被拒绝；语法/事件结构错误包含输入行号。原有 `1e-8` 美元记账单位、24 位成交小数限制和资金/持仓校验继续适用。输出带输入原字节 SHA-256、导入前日志头和接受后的账本摘要。

Python 接入也可以直接调用：

```python
from ledgerx import Ledger, load_events

ledger = Ledger.load("imported.jsonl")
events, source_digest = load_events("examples/ingestion_events.jsonl")
records = ledger.append_batch(events)
```

返回值每一项对应一行输入，重试行会引用原记录，因此返回序号可能重复或不是递增。`append_batch` 不自动保存；上述内存操作成功后需要调用 `ledger.save` 才写入磁盘。若需要组合的文件接入，使用 `ingest_journal` 或 CLI，避免自己循环追加再分次保存。

## 这些保证的边界

`--expected-head` 可检查独立保存的导入前日志头；若导入实际成功而响应丢失，持有旧头的重试会报检查点不一致，应先验证当前日志，再用确认后的头重试。它不是文件锁，不能防止另一个进程在读取与发布之间写入。

本功能仍要求单一日志写入者。一个批次在内存中的全有或全无、文件原子替换，以及持久化后的重试识别，是不同保证；这里没有跨进程事务、消息队列确认、网络请求身份、目录 fsync 的掉电耐久性保证或“端到端 exactly once”。SHA-256 识别所读文件和日志链，不能证明上游记录真实。

## 面试时可以展开的设计问题

可以从“单笔原子性不足以保证整批原子性”开始，再解释为何重试判定要同时比较 ID 和内容，而不是简单去重。对应[回归测试](../tests/test_ingestion.py)验证：后半批余额不足后的内存/磁盘回滚、同 ID 改价、批内重复、混合旧事实与新事实、输入迭代器中断，以及文件替换故障时没有成功输出或残留临时文件。已有财务规则和历史日志格式继续使用同一套重放，新增入口没有改动历史成本或估值口径。
